Introduction to DSA & Go Memory Model

Why data structures matter in Go. Stack vs. Heap allocation, the cost of garbage collection, escape analysis (`go build -gcflags='-m'`), and understanding asymptotic growth rates.

1. Concept & Visual Architecture

In Go, algorithmic efficiency and performance stem from understanding memory layout, pointer indirection, and value semantics. Study the visual representation below:

2. Canonical Problem

🎯 Problem: Operation Counting & Growth Rates

Demonstrate the concrete difference between linear O(n) scan and quadratic O(n²) pair comparisons for input size n.

Key Algorithmic Insight: Big-O measures work scaling as input grows. When n grows 1,000x from 1,000 to 1,000,000, linear work grows 1,000x, while quadratic work grows 1,000,000x.
3. Intuition & Mental Model

Big-O doesn't measure runtime in seconds because different machines have different CPU speeds. Instead, it measures how the count of operations grows when the input n multiplies. In Go, understanding whether data escapes to the heap or lives on the 2KB goroutine stack directly determines whether your program allocates memory.

🪜 Step-by-Step Algorithmic Strategy

1
Identify the primary input size n (e.g. length of slice).
2
Count how many times the most frequent operation executes relative to n.
3
Drop lower-order terms and constant coefficients (e.g. 3n² + 5n + 10 becomes O(n²)).
4
Check Go escape analysis using `go build -gcflags='-m'` to verify if variables stay on stack or trigger GC heap allocation.
4. Structured Pseudocode

Before looking at Go syntax, study the language-agnostic logic. Trace this mentally with sample inputs:

Algorithm Pseudocode Language Independent 
FUNCTION compareOperations(n):
    linearOps = 0
    FOR i FROM 0 TO n - 1:
        linearOps = linearOps + 1      // Work scales linearly: O(n)

    quadraticOps = 0
    FOR i FROM 0 TO n - 1:
        FOR j FROM 0 TO n - 1:
            quadraticOps = quadraticOps + 1  // Work explodes quadratically: O(n²)

    RETURN linearOps, quadraticOps
⚠️ Common Pitfalls & Edge Cases
Micro-optimizing inside loops when the true bottleneck is an O(n²) nested loop or unnecessary heap escapes. Always address the asymptotic Big-O class first before tuning constants.

package main

import "fmt"

// CountOps demonstrates O(n) vs O(n^2) operation counts
func CountOps(n int) (int, int) {
	linearOps := 0
	for i := 0; i < n; i++ {
		linearOps++ // Executes exactly n times
	}

	quadraticOps := 0
	for i := 0; i < n; i++ {
		for j := 0; j < n; j++ {
			quadraticOps++ // Executes n * n times
		}
	}
	return linearOps, quadraticOps
}

func main() {
	for _, n := range []int{10, 100, 1000} {
		lin, quad := CountOps(n)
		fmt.Printf("n=%-4d  O(n): %-6d  O(n^2): %d\n", n, lin, quad)
	}
}
